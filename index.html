Vibe coding that doesn’t tangle as it grows 기능이 늘어도 꼬이지 않는 바이브코딩

Ask an AI to build a web service and the screens come out fine. Then login, a database, and payments get attached — and the code starts to tangle. The T3 Stack fixes the stack before the AI writes a line: one type definition flows from the database through the server to the screen, so when the AI changes the structure, the type checker catches it first. AI에게 웹 서비스를 만들라고 하면 화면은 잘 나온다. 그런데 로그인·데이터베이스·결제가 붙는 순간 코드가 꼬이기 시작한다. T3 Stack은 AI가 코드를 쓰기 전에 스택을 정해두는 방법이다. 데이터베이스부터 서버를 거쳐 화면까지 타입 정의 하나가 이어지므로, AI가 구조를 바꿔도 타입 검사가 먼저 걸러낸다.

01

The problem: screens are easy, services are not문제: 화면은 쉬운데, 서비스는 어렵다

Vibe coding — describing what you want and letting an AI write the code — is fast at visible things. The trouble starts where pieces connect. 바이브코딩, 즉 원하는 것을 말로 설명하면 AI가 코드를 써주는 방식은 눈에 보이는 부분에서 빠르다. 문제는 조각들이 서로 연결되는 지점에서 시작된다.

EASY쉬운 부분

Screens come out well화면은 잘 나온다

Landing pages, forms, and layouts are self-contained. The AI can generate them in one pass and they look right immediately.랜딩 페이지, 입력 폼, 레이아웃은 그 자체로 완결된다. AI가 한 번에 만들어내도 바로 그럴듯하게 보인다.

WHERE IT BREAKS꼬이는 지점

Login · DB · payments로그인 · DB · 결제

Once authentication, stored data, and orders connect, each new feature touches shapes defined somewhere else. The AI edits one side, forgets the other, and the mismatch ships silently.인증, 저장된 데이터, 주문이 연결되면 새 기능마다 다른 곳에 정의된 데이터 형태를 건드리게 된다. AI는 한쪽만 고치고 다른 쪽을 잊고, 그 어긋남은 조용히 배포된다.

THE FIX해법

Decide the stack first스택을 먼저 정한다

Pick a stack where the data’s shape is defined once and checked everywhere. Then the compiler — not a human reviewer — becomes the AI’s supervisor.데이터 형태를 한 번 정의하고 모든 곳에서 검사하는 스택을 고른다. 그러면 사람의 리뷰어가 아니라 컴파일러가 AI의 감독자가 된다.

02

The stack: seven pieces, one language스택 구성: 일곱 조각, 하나의 언어

T3 is not a framework of its own. It is a curated set of TypeScript-first tools, scaffolded by create-t3-app. Every piece is optional — include only what the service needs. T3는 그 자체로 하나의 프레임워크가 아니다. create-t3-app이 한 번에 설치해주는, TypeScript 중심 도구들의 조합이다. 모든 구성품은 선택 사항이라 서비스에 필요한 것만 넣으면 된다.

Next.js Web screens plus server functions in one project (App Router or Pages Router).웹 화면과 서버 기능을 한 프로젝트에서 담당한다 (App Router 또는 Pages Router).
TypeScript Checks the shape of data in code, end to end — the thread that ties the stack together.코드 안에서 데이터 형태를 끝에서 끝까지 검사한다. 스택 전체를 잇는 실이다.

03

Why it works: one type, end to end왜 통하는가: 끝까지 이어지는 하나의 타입

The schema is defined once in the database layer. tRPC infers the server’s types on the client automatically, so the screen and the server can never quietly disagree about a shape. 스키마는 데이터베이스 층에서 한 번만 정의한다. tRPC가 서버의 타입을 클라이언트에 자동으로 추론해주므로, 화면과 서버가 데이터 형태를 두고 조용히 어긋날 수 없다.

Change a field on the left, and every place that still uses the old shape lights up as a compile error on the right — before anything runs. 왼쪽에서 필드 하나를 바꾸면, 옛 형태를 그대로 쓰는 모든 곳이 오른쪽에서 컴파일 오류로 표시된다. 실행해보기 전에 알 수 있다.

Two mistakes the type checker catches for you타입 검사가 대신 잡아주는 실수 두 가지

Try it: run the type check on the hand-written version, then on the T3 version. 직접 눌러보자. 손으로 타입을 따로 적은 버전과 T3 방식으로 연결한 버전을 각각 타입 검사해보는 데모다.

order.tsExample 1 — the price that changed type예시 1 — 타입이 바뀐 가격
// server — price is a number
const item = { name: "Burger set", price: 10000 };

// screen — the AI re-typed it by hand, as a string
const payload = { price: "10000" };
submitOrder(payload);
✗ error TS2345: Type ‘string’ is not assignable to type ‘number’. A person reads 10000 and "10000" as the same value — a program does not.error TS2345: ‘string’ 타입은 ‘number’ 타입에 할당할 수 없다. 사람은 10000과 "10000"을 같은 값으로 읽지만, 프로그램은 다르게 읽는다.
✓ With tRPC, the screen never re-types the shape — it infers price: number from the server, so the string version cannot be written in the first place.✓ tRPC를 쓰면 화면이 형태를 다시 적지 않는다. 서버에서 price: number를 추론하므로, 문자열 버전은 처음부터 쓸 수 없다.
profile.tsExample 2 — the renamed field예시 2 — 이름이 바뀐 필드
// database — field renamed: name → username
model User { id Int; username String }

// screen — still using the old field
<p>{user.name}</p>
✗ error TS2339: Property ‘name’ does not exist on type ‘User’. Without connected types this is a silent blank on the page; with them, it is a compile error the AI must fix.error TS2339: ‘User’ 타입에 ‘name’ 속성이 없다. 타입이 연결돼 있지 않으면 화면에 조용히 빈칸으로 남지만, 연결돼 있으면 AI가 반드시 고쳐야 하는 컴파일 오류가 된다.
✓ The rename propagates through Prisma → tRPC → UI as one type. Every stale usage is listed by the compiler, not hunted down by a person at runtime.✓ 이름 변경이 Prisma → tRPC → UI까지 하나의 타입으로 전파된다. 낡은 사용처는 사람이 실행 중에 찾아다니는 게 아니라 컴파일러가 전부 목록으로 보여준다.

05

The AI rules: one instruction that does the guardingAI 규칙: 감독을 맡는 지시문 한 줄

The rule from the original post is short enough to paste at the start of every AI coding session. It works because each clause maps to a check the toolchain can actually enforce. 원글에서 제시한 규칙은 짧아서 AI 코딩 세션을 시작할 때마다 그대로 붙여 넣을 수 있다. 각 문장이 도구 체인이 실제로 강제할 수 있는 검사와 연결되기 때문에 통한다.

“Develop while maintaining the existing T3 Stack structure. Validate data inputs with Zod, and write it so it passes the type check. Don’t bypass errors with the any type.”

“기존 T3 Stack 구조를 유지하면서 개발해 줘. 데이터 입력값은 Zod로 검증하고, 타입 검사를 통과하도록 작성해 줘. any 타입으로 오류를 우회하지 마.”

RULE 1

Keep the structure구조를 유지한다

The AI works inside the scaffold’s folders and patterns instead of inventing its own layout per feature. Consistency is what makes the types connect.AI가 기능마다 자기 방식의 배치를 만들지 않고, 스캐폴드가 정한 폴더와 패턴 안에서 작업한다. 그 일관성이 타입 연결을 가능하게 한다.

RULE 2

Validate with ZodZod로 검증한다

Every tRPC procedure declares a Zod input schema. Unvalidated input never crosses a procedure boundary — types alone can’t check real user data.모든 tRPC 프로시저는 Zod 입력 스키마를 선언한다. 검증되지 않은 입력은 프로시저 경계를 넘지 않는다. 타입만으로는 실제 사용자 데이터를 검사할 수 없기 때문이다.

RULE 3

No any, no silencingany 금지, 오류를 잠재우지 않는다

any and stray @ts-ignore comments switch the checker off exactly where it matters. A type error is the AI’s signal to fix its own change — if the type is genuinely unknown, narrow it with Zod first.any와 무분별한 @ts-ignore는 정작 중요한 지점에서 검사기를 꺼버린다. 타입 오류는 AI가 자기 변경을 고치라는 신호다. 타입을 정말 모르는 값이라면 먼저 Zod로 좁힌 뒤 타입을 정한다.

06

Workflow: the order matters워크플로: 순서가 중요하다

Six steps, in this order. The pattern underneath all of them: define shapes once, let the tools check every use. 여섯 단계, 이 순서대로. 전체를 관통하는 원칙은 하나다. 형태는 한 번 정의하고, 사용하는 모든 곳은 도구가 검사하게 한다.

  1. Scaffold, then commit the clean state스캐폴드하고, 깨끗한 상태를 먼저 커밋한다

    Run create-t3-app and commit before any feature work, so every later change is measured against a known-good structure.create-t3-app을 실행하고 기능을 붙이기 전에 커밋한다. 이후의 모든 변경을 정상 구조와 비교할 수 있게 하기 위해서다.

  2. Define the data model first데이터 모델부터 정의한다

    Write the Prisma schema or Drizzle tables before screens. The schema is the single source of truth for shapes — everything else derives from it.화면보다 먼저 Prisma 스키마나 Drizzle 테이블을 쓴다. 스키마가 형태의 유일한 기준이고, 나머지는 전부 거기서 파생된다.

  3. Add tRPC procedures with Zod inputsZod 입력을 갖춘 tRPC 프로시저를 추가한다

    Each procedure validates its input with a Zod schema. Never accept unvalidated input at a procedure boundary.각 프로시저는 Zod 스키마로 입력을 검증한다. 프로시저 경계에서 검증되지 않은 입력은 절대 받지 않는다.

  4. Build screens on inferred types추론된 타입 위에서 화면을 만든다

    The UI consumes the tRPC client’s inferred types. Do not redeclare the same shapes by hand on the client — a hand-written duplicate is exactly where drift starts.UI는 tRPC 클라이언트가 추론한 타입을 그대로 쓴다. 클라이언트에서 같은 형태를 손으로 다시 선언하지 않는다. 손으로 적은 중복 정의가 바로 어긋남이 시작되는 곳이다.

  5. Typecheck and build after every feature기능마다 타입 검사와 빌드를 돌린다

    Run npm run typecheck and the build after each feature. Treat a type error as the AI’s instruction to fix its change, not as noise to silence.기능을 하나 붙일 때마다 npm run typecheck와 빌드를 실행한다. 타입 오류는 잠재울 소음이 아니라, AI가 자기 변경을 고치라는 지시로 취급한다.

  6. Never bypass with anyany로 우회하지 않는다

    No any to dodge an error, and no @ts-ignore / @ts-expect-error without a written reason in a comment. Unknown data gets narrowed with Zod, then typed.오류를 피하려고 any를 쓰지 않고, 코멘트에 이유를 적지 않은 @ts-ignore / @ts-expect-error도 쓰지 않는다. 모르는 데이터는 Zod로 좁힌 뒤 타입을 정한다.

07

When to use it — and when to skip it쓸 때와 건너뛸 때

Use T3 whenT3가 맞는 경우

  • The service keeps growing: signup, stored data, a dashboard, orders, order history — features that share data shapes.서비스가 계속 자라는 경우: 회원가입, 데이터 저장, 대시보드, 주문, 주문 내역처럼 데이터 형태를 공유하는 기능들.
  • An AI writes most of the code: the more code is delegated, the more the project needs a structure that verifies the rules the code must follow.AI가 코드 대부분을 쓰는 경우: 위임하는 코드가 많을수록, 코드가 지켜야 할 규칙을 검증해주는 구조가 더 필요해진다.
  • You already build with Next.js + TypeScript: the frontend half is familiar; tRPC, Prisma, and NextAuth are the only new pieces.이미 Next.js + TypeScript로 만들고 있는 경우: 프론트엔드 절반은 익숙하고, 새로 배우는 조각은 tRPC, Prisma, NextAuth뿐이다.

Skip T3 when건너뛰는 경우

  • It’s a simple intro or landing page: Next.js + Tailwind CSS alone is enough. There is no shared shape to protect.단순한 소개·랜딩 페이지인 경우: Next.js + Tailwind CSS만으로 충분하다. 지킬 공유 형태 자체가 없다.
  • The codebase already runs on another stack: don’t force a migration to T3. The benefit comes from starting connected, not from the brand name.이미 다른 스택으로 돌고 있는 코드베이스인 경우: T3로 억지 마이그레이션하지 않는다. 이점은 이름이 아니라 처음부터 연결된 구조에서 나온다.
  • You expect type checking to be a security boundary: it isn’t. Auth rules, authorization checks, and input validation still need explicit design.타입 검사를 보안 경계로 기대하는 경우: 타입 검사는 보안이 아니다. 인증 규칙, 권한 검사, 입력 검증은 별도로 명시적으로 설계해야 한다.

Keep in mind: payments are not part of the T3 Stack itself. A T3 app takes payments by integrating Stripe — see the t3-stripe example below — the same way any Next.js app would.기억할 점: 결제는 T3 Stack 자체의 구성품이 아니다. T3 앱은 다른 Next.js 앱과 마찬가지로 Stripe를 연동해 결제를 받는다. 아래 t3-stripe 예시를 참고하면 된다.

Where this fits: a small-business ordering SaaS어디에 맞나: 소상공인 직접 주문 SaaS

    

    

      

        A direct-ordering service for small shops needs exactly four things to work: login, a database, orders, and a dashboard. Those are four of the T3 pieces, off the shelf. Add Stripe for payment and the backend shape is complete — which is why this stack pairs well with the build-it-by-assembling approach: the parts exist, they are type-connected, and an AI can extend them without quietly breaking the seams.
        소상공인용 직접 주문 서비스가 동작하려면 정확히 네 가지가 필요하다. 로그인, 데이터베이스, 주문, 대시보드. 이 넷은 T3 구성품 중 네 개와 그대로 겹친다. 여기에 결제로 Stripe를 붙이면 백엔드 형태가 완성된다. 그래서 이 스택은 ‘조립해서 만드는’ 접근과 잘 맞는다. 부품이 이미 있고, 타입으로 연결돼 있으며, AI가 확장해도 연결 부위가 조용히 깨지지 않는다.
      

      

        It also builds on a familiar base: existing Next.js + React + TypeScript side projects already cover the frontend half of T3. The genuinely new pieces to learn are tRPC, Prisma/Drizzle, and NextAuth.js — three tools, not a new language.
        익숙한 기반 위에 올라간다는 점도 있다. 기존의 Next.js + React + TypeScript 사이드 프로젝트가 이미 T3의 프론트엔드 절반을 커버한다. 새로 배울 조각은 tRPC, Prisma/Drizzle, NextAuth.js 셋뿐이다. 새 언어가 아니라 도구 세 개다.
